### 4. Surge Pricing Service (SurgePricingService.cs - 11 KB)
```
SURGE ALGORITHM:
┌─────────────────────────────────────────────────────────────┐
│ Input: Latitude, Longitude, Current Time                    │
│   ↓                                                          │
│ Step 1: Quantize to Grid Cell (0.01° grid)                  │
│   └─ Lat: -23.5505 → -23.56 (grid)                         │
│   └─ Lng: -46.6333 → -46.64 (grid)                         │
│   ↓                                                          │
│ Step 2: Get Metrics                                         │
│   └─ Demand = Redis GET surge:demand:{cell}                 │
│   └─ Supply = Redis GET surge:supply:{cell}                 │
│   ↓                                                          │
│ Step 3: Calculate Ratio                                     │
│   └─ Ratio = Demand / Supply (default supply = 1)           │
│   ↓                                                          │
│ Step 4: Map to Multiplier                                   │
│   ├─ Ratio ≤ 0.5    → 1.0x (plenty of drivers)             │
│   ├─ Ratio ≤ 1.0    → 1.25x (balanced)                     │
│   ├─ Ratio ≤ 2.0    → 1.75x (high demand)                  │
│   ├─ Ratio ≤ 4.0    → 2.5x (very high)                     │
│   └─ Ratio > 4.0    → 3.0x (capped at max)                 │
│   ↓                                                          │
│ Output: Multiplier (1.0x - 3.0x)                            │
└─────────────────────────────────────────────────────────────┘

METRICS RECORDING:
├─ RecordRideDemand():  INCR surge:demand:{cell}  (30m TTL)
├─ RecordDriverSupply(): INCR/DECR supply:{cell} (1h TTL)
├─ GetMetrics():        Read current values
└─ GetHistory():        LRANGE history:{cell}    (7d TTL)
```

## DECISION RATIONALE

| Decision | Why | Alternative | Trade-off |
|----------|-----|-------------|-----------|
| Redis GEO | Fast geospatial queries | PostGIS (PostgreSQL) | In-memory only; needs cache |
| Haversine | Standard great-circle distance | Vincenty (more accurate) | Overkill precision for use case |
| 0.01° grid | ~1km granularity at equator | 0.001° (100m) | Memory vs precision |
| 70/30 weight | Distance dominates matching | 50/50 or reverse | Closer drivers more reliable |
| 30s expiration | Short to avoid missed offers | 60s (longer) | UX responsiveness vs acceptance rate |
| List history | Compact storage + replay capability | Separate time-series DB | Only last 1000 points stored |
| No transactions | Location is eventually consistent | ACID transactions | Latency vs strong consistency |
